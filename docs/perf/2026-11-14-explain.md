## Proposal: stored running balance (ruling T10-b, parked until after Phase 1)

### Why the usage ledger is slow

`usageLedgerPage` (`apps/api/src/services/usage-ledger.ts`) computes `balance_after` and `held_after` with `sum(...) over (partition by organization_id order by created_at, id)` over every ledger row of the organization. The date range, kind, channel and keyset filters and the `order by created_at desc` all apply to the window's output, so Postgres cannot push them below it. Every page reads the whole ledger in ascending order, runs the window, then sorts the whole result descending to take 51 rows. At 300,000 entries that is 435–782 ms per page on the 2026-11-14 re-run (1.1–2.0 s before), whatever the page or the filter. The plan is `Limit > Sort > Subquery Scan > WindowAgg > Index Scan using ledger_entry_org_created_idx`.

### Rewrites tried and rejected

- Running the window descending and deriving `balance_after = total - (sum of the later rows)` is exact, and it removes the sort. But it still needs the organization total (a full aggregate, about 90 to 130 ms) on every page, and a deep or old-range page still streams every newer row (415 ms at 150,000 rows deep). Still over budget, and it changes money code, so it was not landed (ruling T10-b).
- Pushing the filters below the window would change the balances. A filter must never change a row's balance.

### The fix: store each row's running totals at insert

Shape: two columns on `ledger_entry`, both `bigint not null`, set once by the app at insert:

- `balance_after_micros`: the wallet balance after this entry,
- `held_after_micros`: the held total after this entry.

The table is append-only for the app role (`sql/rls.sql`), so a stored value never goes stale. A separate `ledger_balance` table keyed by entry id would also work, but it adds a join to every page and a second insert to every write, for no gain.

The route then becomes a plain filtered keyset on `ledger_entry`: `where organization_id = $org [and created_at >= $start and created_at < $end] [and kind = $kind] [and ref_type in (...)] [and (created_at, id) < ($c, $id)] order by created_at desc, id desc limit 51`, served by `ledger_entry_org_created_idx` scanned backwards. It reads about 51 rows (more under a narrow kind or channel filter), like `wallet.ledger.*`, which already passes in 2 ms. The channel filter should compare `ref_type` against the list for the channel (`'call'` for voice, the complement for `other`) instead of the `CASE`, so it stays a plain comparison.

### How it stays correct on insert

1. Every write already takes the wallet row lock: `reserve`, `capture`, `release`, `adjust` and `credit` call `walletOf(tx, orgId, true)` (`SELECT ... FOR UPDATE`) before they insert. Under that lock the insert reads the previous totals and adds its deltas: `select balance_after_micros, held_after_micros from ledger_entry where organization_id = $org order by created_at desc, id desc limit 1`, an index lookup.
2. One gap must close first: `ensureWallet` inserts the starter credit without the lock. It must take the same lock, or compute its totals inside the same statement.
3. The stored order must match the window's order. Today `created_at` defaults to `now()`, the transaction start time. A transaction that started earlier but waited on the wallet lock commits a smaller `created_at` after a later one, so a running sum in insert order would differ from the `(created_at, id)` order the window uses. The insert must therefore set `created_at = clock_timestamp()` after it takes the lock, so the insert order and the `(created_at, id)` order agree. Each insert then reads the newest row and appends a newer one.
4. Add a CHECK `held_after_micros >= 0`, and a deferred verification in the test suite: for every organization, the stored totals equal the window over `(created_at, id)`.

### Migration and backfill

- Add the two columns as nullable, backfill them once with the current window (one pass per organization, in batches), then set them `not null`. No other data changes.
- Behaviour proof: an oracle test runs the current window query, verbatim, against the new route on a seeded ledger, including filters, deep cursors and concurrent reserves, and compares every row's `balanceAfterMicros` and `heldAfterMicros`.

### Expected result

`usage.ledger.first`, `.deep` and `.filtered` drop from 435–782 ms on the 2026-11-14 re-run (1.1–2.0 s before) to the `wallet.ledger.*` range (about 2 ms), and the T10-b allowlist entry goes away.
